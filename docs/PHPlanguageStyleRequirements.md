Требования к стилю языка PHP (Coding Standards)

1. Определение

Требования к стилю языка (стиль кодирования) — это совокупность правил и рекомендаций, определяющих, каким образом должен быть написан исходный код программы. Эти правила направлены на обеспечение единообразия структуры кода, повышение его читаемости, упрощение сопровождения и снижение вероятности возникновения ошибок.

В процессе разработки программного обеспечения код читается значительно чаще, чем пишется. Именно поэтому единый стиль кодирования играет ключевую роль при командной разработке, ревью кода, тестировании и дальнейшей поддержке проекта.

Применение стандартов кодирования позволяет:

обеспечить единый внешний вид кода независимо от разработчика
ускорить понимание логики программы другими участниками команды
снизить количество ошибок за счёт предсказуемой структуры
упростить автоматическую проверку качества кода
повысить переносимость решений между проектами

2. Организация стандартов PHP

Стандарты кодирования PHP разрабатываются организацией PHP-FIG (PHP Framework Interoperability Group). Эта группа объединяет разработчиков различных PHP-фреймворков и библиотек с целью выработки единых рекомендаций.

Основные документы, определяющие стиль кодирования:

PSR-1 — базовые требования к структуре кода
PSR-12 — расширенные правила форматирования
PER Coding Style — современное развитие стандартов

PSR (PHP Standards Recommendations) представляют собой официальные рекомендации, которые не являются обязательными на уровне языка, но де-факто используются большинством профессиональных проектов.

3. PSR-1: Basic Coding Standard

PSR-1 определяет базовые требования к структуре PHP-кода и правила именования.

3.1 Общие требования к файлам

Каждый PHP-файл должен использовать только стандартные PHP-теги открытия:

<?php

Допускается использование сокращённого тега вывода:

<?= $value ?>

Использование других вариантов тегов (например, коротких тегов <?) не допускается, так как они могут быть отключены в конфигурации PHP.

Файлы должны быть сохранены в кодировке UTF-8 без BOM. Это необходимо для корректной работы с текстовыми данными и предотвращения неожиданных ошибок вывода.

Каждый файл должен иметь чёткое назначение. Он должен либо:

содержать только объявления (классы, интерфейсы, функции, константы),
либо выполнять действия (например, подключение файлов, вывод данных, выполнение логики).

Смешивание этих подходов в одном файле запрещено, так как это усложняет повторное использование и тестирование кода.

3.2 Именование элементов

Имена элементов программы должны быть осмысленными, отражать назначение и соблюдать единый стиль.

Имена классов должны записываться в стиле PascalCase (StudlyCaps). Это означает, что каждое слово в имени начинается с заглавной буквы, без использования подчёркиваний.

class OrderManager
{
}

Методы и функции должны использовать стиль camelCase. Первое слово пишется с маленькой буквы, последующие — с заглавной.

public function calculateTotalPrice()
{
}

Константы должны записываться в верхнем регистре с разделением слов символом подчёркивания.

const MAX_CONNECTIONS = 100;

Такое разделение позволяет визуально отличать разные типы сущностей в коде.

3.3 Пространства имён (namespace)

Каждый класс должен находиться в собственном пространстве имён. Это необходимо для предотвращения конфликтов имён и логической организации проекта.

namespace App\Services;

class PaymentService
{
}

Структура пространства имён должна соответствовать структуре каталогов проекта. Обычно используется стандарт PSR-4 для автозагрузки классов.

3.4 Побочные эффекты (Side Effects)

Побочные эффекты — это выполнение кода при подключении файла. К ним относятся:

вывод данных (echo, print)
подключение других файлов (include, require)
изменение глобального состояния

PSR-1 требует, чтобы файл не содержал одновременно объявления и побочные эффекты.

Некорректный пример:

<?php

include 'config.php';

function test()
{
}

Корректный подход — разделение логики:

<?php

function test()
{
}


4. PSR-12: Extended Coding Style

PSR-12 является расширением PSR-1 и определяет строгие правила форматирования кода.

4.1 Форматирование файлов

Каждый файл должен использовать символ перевода строки LF (\n). Использование других форматов может привести к проблемам совместимости между операционными системами.

Файл должен заканчиваться одной пустой строкой. Это обеспечивает корректную работу некоторых инструментов и систем контроля версий.

Закрывающий тег ?> в PHP-файлах, содержащих только PHP-код, не используется. Это предотвращает случайный вывод данных.

4.2 Ограничения длины строки

Рекомендуемая длина строки составляет не более 80 символов. Это связано с удобством чтения кода.

Максимальная допустимая длина строки — 120 символов. Превышение этого значения допускается только в исключительных случаях, например, при работе с длинными строками или URL.

4.3 Отступы и выравнивание

Для отступов используются только пробелы, строго 4 пробела на один уровень вложенности.

Использование табуляции запрещено, так как разные редакторы могут отображать её по-разному.

Каждый уровень вложенности должен быть визуально очевиден.

4.4 Общие правила оформления

Каждое выражение должно находиться на отдельной строке. Это упрощает чтение и отладку.

Запрещены пробелы в конце строки, так как они не несут смысловой нагрузки и могут создавать проблемы при сравнении файлов.

Допускается использование пустых строк для логического разделения блоков кода.

4.5 Управляющие конструкции

Управляющие конструкции (if, else, for, while) должны оформляться строго с фигурными скобками, даже если тело состоит из одной строки.

if ($isActive) {
    process();
} else {
    stop();
}

Скобки открываются на той же строке, что и условие, а закрываются на новой строке.

4.6 Функции и методы

Аргументы функций должны быть перечислены через запятую с пробелом после неё.

Тело функции должно начинаться с новой строки.

function calculateSum($a, $b)
{
    return $a + $b;
}
4.7 Классы и структуры

Каждый класс объявляется в отдельном файле.

Методы класса должны быть разделены пустыми строками для повышения читаемости.

class UserService
{
    public function createUser()
    {
    }

    public function deleteUser()
    {
    }
}
5. PER Coding Style

PER (PHP Extended Recommendation) — современный стандарт, развивающий PSR-12.

Он уточняет и расширяет правила, уделяя больше внимания читаемости и единообразию.

5.1 Основные принципы

PER полностью совместим с PSR-1 и использует его как основу.

Особое внимание уделяется:

визуальной структуре кода
последовательности оформления
предсказуемости форматирования
5.2 Требования к коду

Код должен быть организован таким образом, чтобы его можно было легко читать без дополнительного анализа.

Не допускается:

размещение нескольких инструкций в одной строке
наличие лишних пробелов
нарушение логической структуры
5.3 Читаемость и структура

Допускается использование пустых строк для разделения логических блоков, но их количество должно быть оправдано.

Код должен быть сгруппирован по смыслу:

объявления
бизнес-логика
вспомогательные методы

6. Общие требования и ограничения

Обязательные требования:

использование кодировки UTF-8 без BOM
соблюдение PSR-1
применение PSR-12 или PER
использование пространств имён
отступы только пробелами (4 пробела)
единый стиль именования

Запрещено:

использование табуляции
закрывающий тег ?> в PHP-only файлах
смешивание объявлений и исполняемого кода
несколько инструкций в одной строке
пробелы в конце строк

7. Инструменты автоматизации

Для обеспечения соответствия стандартам используются специальные инструменты.

PHP-CS-Fixer автоматически исправляет стиль кода:

php-cs-fixer fix

PHP_CodeSniffer анализирует код и выявляет нарушения:

phpcs

Использование этих инструментов рекомендуется интегрировать в процесс разработки и систему контроля версий.

8. Заключение

Стандарты кодирования являются важной частью разработки на PHP. Их соблюдение обеспечивает единый стиль, упрощает взаимодействие между разработчиками и повышает качество программного продукта.

Применение стандартов PSR и PER позволяет создавать поддерживаемый, читаемый и масштабируемый код, соответствующий современным требованиям разработки.
